## Scope and decision rule

This entry records one upstream project's reporting rule: the Linux kernel security team's page on how to report security bugs to the kernel. It governs reports sent to the kernel security list and to kernel maintainers. It is not a rule for distributions, for other projects, or for CVE handling, and it is not general guidance on coordinated disclosure.

The page treats four items as required for any security bug report: “The following information are absolutely necessary in **any** security bug report” (`S071.txt:17-18`). Those four are the affected kernel version range, the problem description, a reproducer and the triggering conditions (listed at `S071.txt:20-47`).

Decision rule: a package may describe a Linux kernel report as carrying the page's four necessary items only when all four are present and the version is a stable identifier. A package may describe the postponement of a kernel fix's publication only in the terms of the table below. A package may not describe an issue that cannot be reproduced as a security bug.

| observed question | kernel text | package consequence |
|---|---|---|
| Does the report name a kernel version? | “with no version indication, your report will not be processed” (`S071.txt:20-21`) | Record the version field as missing and the report as not processable under this page. A time-dependent label is not a version: the page rejects “latest mainline” (`S071.txt:21-22`, paraphrased). |
| What counts as a stable identifier? | “A stable identifier such as a commit ID or an exact version is required” (`S071.txt:22-23`) | A commit ID and an exact version are the page's examples of a stable identifier; do not substitute a label that changes over time. |
| Does a distro kernel version satisfy the field? | “Versions designating kernels not coming from kernel.org (such as distro kernels) are meaningless to maintainers” (`S071.txt:23-24`) | A distro version string does not by itself identify the kernel for the maintainers; record the kernel.org identifier the page asks for. |
| May the reproducer be a binary? | “Binary-only executables are not accepted” (`S071.txt:39-40`) | The page's examples of an acceptable reproducer are source code, a shell script, a sequence of instructions or a file-system image (`S071.txt:37-39`); a binary-only executable fails the field. |
| Is an issue that cannot be reproduced a security bug? | “By definition if an issue cannot be reproduced, it is not exploitable, thus it is not a security bug” (`S071.txt:41-43`) | Keep the item out of security-bug status while reproduction is absent; record it as an unconfirmed candidate. |
| Does the report cross a trust boundary? | “consider whether the issue actually crosses a trust boundary on such a system” (`S071.txt:92-93`) | Record the trust boundary the issue crosses on a correctly configured production system; an issue that crosses none belongs on the normal bug channel the page names (`S071.txt:84-87`), not the security list. |
| Does an AI-assisted find stay private? | “If you resorted to AI assistance to identify a bug, you must treat it as public” (`S071.txt:95-96`); “While you may have valid reasons to believe it is not” (`S071.txt:96`) | Record the finding as AI-assisted and handle it as public, which is the page's handling rule; the page gives its reason (such finds surface simultaneously across researchers, `S071.txt:96-98`) and states no embargo for it. |
| Where does the reproducer go for an AI-assisted find? | “do not publicly share a reproducer, as this could cause unintended harm” (`S071.txt:99`); “the reproducer should only be shared upon maintainers' request” (`S071.txt:210-211`) | State that a reproducer exists and is available on maintainer request; keep it out of the public text. The page gives this instruction for the AI-assisted case. |
| What channel carries the report? | “Reports are to be sent over e-mail exclusively” (`S071.txt:257`) | The page names e-mail as the only report channel. |
| Who receives the report? | “If there are two or fewer recipients in your message” (`S071.txt:271-272`); “you must also always Cc: the Linux kernel security team” (`S071.txt:272-273`); “For larger teams, Cc: the Linux kernel security team for your first few reports or when seeking specific help” (`S071.txt:275-276`) | Record the maintainer recipient count. With two or fewer recipients the security team must be Cc'd; with larger teams the page asks for that Cc for a reporter's first few reports or when seeking help. |
| What starts the kernel's postponement clock? | “Once a robust fix has been developed, the release process starts” (`S071.txt:305`); “Fixes for publicly known bugs are released immediately” (`S071.txt:305-306`) | Anchor any kernel postponement date to the release-process start, which follows a robust fix; the page defines no report-date clock, and a publicly known bug is not postponed. |
| How long may publication of a fix be postponed? | “this may be postponed at the request of the reporter or an affected party” (`S071.txt:309-310`); “for up to 7 calendar days from the start of the release process, with an exceptional extension to 14 calendar days” (`S071.txt:310-311`); “if it is agreed that the criticality of the bug requires more time” (`S071.txt:312`) | Record the release-process start date. A reporter or affected party may request a postponement of up to 7 calendar days from that start for a publicly undisclosed bug; 14 days is an exceptional extension that needs the agreement the page mentions but does not say who gives. A longer deferral is unsupported by S071. |
| Which deferral reason is valid? | “only valid reason for deferring the publication of a fix is to accommodate the logistics of QA and large scale rollouts which require release coordination” (`S071.txt:313-315`) | Record QA and large-scale-rollout release coordination as the reason; other reasons are not supported by this page. |

## Overlap and novelty

Already held in this corpus:

- F02 (`corpus/knowledge/coordinated-disclosure-timelines.md:7-17`) requires a timeline to name the policy, the clock-starting event, the stated interval, the patch/publication relationship and any documented extension, and forbids transplanting another coordinator's interval (line 17). This entry applies that rule to the kernel's own record. The 7-day and 14-day figures are S071's, bound to the release-process trigger. They must not be read into F02's CERT/CC 45-day row (`corpus/knowledge/coordinated-disclosure-timelines.md:22`) or its Project Zero 30-day and 14-day grace rows (`corpus/knowledge/coordinated-disclosure-timelines.md:24-25`).
- F04 (`corpus/knowledge/ai-assisted-finding-validation.md:7-8,15`) holds that an AI-originated finding stays a candidate until reproduction and an independent reviewer are recorded. S071 does not require a reviewer distinct from the producer. Its reporter-side check is that a reproducer which fails should lead to the report's validity being questioned: “the validity of the report should be seriously questioned” (`S071.txt:208-209`). F04's validation record and S071's intake duties are separate checks.
- F15 (`corpus/knowledge/vendor-third-party-finding-coordination.md:91-96`; `corpus/README.md:309`) holds the rule to record which party coordinates a multi-party finding. S071 places distro and vendor disclosure coordination with other groups: “other groups focus on fixing issues in distros and coordinating disclosure between operating system vendors” (`S071.txt:333-334`). For a kernel report, S071 therefore records no kernel-security-team coordination role for distro or vendor disclosure.
- F10 (`corpus/README.md:211`) holds a vendor's published policy as a standing first-party statement. The kernel security team is an upstream project's maintainers, not a vendor, so F27 is a separate row rather than an F10 member; what it shares with F10 is only the first-party-statement standard.
- F07 (`corpus/README.md:208`) and F25 (`corpus/README.md:591`) hold CVE assignment and the CVE record format. S071 has a CVE section (`S071.txt:359-366`); this entry does not record it as CVE policy.

What is new here:

1. The kernel's required-fields intake contract. A maintainer-side list of four necessary fields, with a stated consequence for a missing version (`S071.txt:20-21`). F02 and F04 hold timelines and validation records, not an upstream intake gate.
2. The AI-assisted-report handling. The page treats an AI-assisted find as public, keeps the reproducer out of the public text, and asks for a concise plain-text report that sticks to verifiable facts: “Please stick to verifiable facts” (`S071.txt:201`). For the AI assistant it lists two MUST items: the plain-text report with the four necessary items and a recipients section (`S071.txt:239-250`). A proposed fix is listed only as highly desirable for any report (`S071.txt:49-58`) and as advice for AI tools (`S071.txt:213-219`).
3. The 7/14-day ceiling as an upstream-maintainer rule. It caps a postponement that the reporter or an affected party requests, so it binds the requesting reporter; it runs from the release-process start rather than the report date and admits one valid reason.

## Limits

- One project's rule: the Linux kernel security team's page. It is not law, not a general coordinated-disclosure standard and not guidance for other projects or distributions.
- Out of this entry: kernel patch-format, Fixes-tag, checkpatch and get_maintainer duties (`S071.txt:213-219`, `S071.txt:232-237`) are kernel engineering, not recorded here; CVE assignment (`S071.txt:359-366`) and the linux-distros coordination detail (`S071.txt:329-357`) are not recorded as rules. ## Falsifiable package rule

When a package states the publication deferral for a kernel security fix, check it against S071 in this order. (1) The start date must be the release-process start, after a robust fix exists, not the report date (`S071.txt:305`). (2) The deferral must be at most 7 calendar days from that start (`S071.txt:310-311`). (3) A longer deferral, up to 14 days, is an exceptional extension that needs agreement (`S071.txt:312`). A package that records a 21-day kernel embargo with no other source is unsupported by S071.

## Rejected over-generalizations

- Rejected claim: every Linux kernel report gets a 7-day embargo. S071 describes a postponement that may be requested by the reporter or an affected party, and caps it: “this may be postponed at the request of the reporter or an affected party” (`S071.txt:309-310`). It is a ceiling on requested postponement, not a default embargo for every report.
- Rejected claim: an AI-assisted finding may go only to the security list. S071 says to avoid a public list at this stage unless the issue is public or trivial to discover, and names “or use of AI-based tools” (`S071.txt:117`) as one such case. The page therefore does not route AI-assisted findings only to the security list.
- Rejected claim: the kernel security team coordinates disclosure with distributions. S071 says the security team “solely focuses on getting bugs fixed” (`S071.txt:332`) and attributes distro and vendor coordination to other groups (`S071.txt:333-334`).

IETF Informational RFC, April 2022, E. Foudil and Y. Shafranovich; it defines a format and defers the rest of disclosure to other documents ("Other details of vulnerability disclosure are outside the scope of this document", S063.txt:L104 §1.1). Its own stated relation to a vendor's other resources is subordinate: "The \"security.txt\" file is intended to be complementary and not a substitute or replacement for other public resources" (S063.txt:L115 §1.1). Everything below is a rule of this file's format, never a claim about any named organization's practice.

## Claim 1 — two fields are REQUIRED and every other field is optional by default
> "Unless otherwise stated, all fields MUST be considered optional." — S063.txt:L189 (§2.5)
> "This field MUST always be present in a \"security.txt\" file." — S063.txt:L227 (§2.5.3 `Contact`)
The exceptions are exactly two fields: `Contact` (§2.5.3) and `Expires` (§2.5.5, Claim 3), each carrying the same requirement in its own definition. The remaining six defined fields are optional — `Acknowledgments` §2.5.1, `Canonical` §2.5.2, `Encryption` §2.5.4, `Hiring` §2.5.6, `Policy` §2.5.7, `Preferred-Languages` §2.5.8 — and a field added later through the IANA registry is optional too: "Any fields registered via that process MUST be considered optional." (§2.4). Field names are case-insensitive and a value is a URI where the definition says so (§2, §2.5.3 spells an email address `mailto:`), repeated `Contact` lines are preference-ordered (§2.5.3), and readers must tolerate the unknown: "researchers MUST ignore any fields they do not explicitly support" (§2.4).

## Claim 2 — `Encryption` is a pointer to a key, never the key, and PGP is the recommended machinery
> "When the value of this field is an email address, it is RECOMMENDED that encryption be used" — S063.txt:L235 (§2.5.3)
> "Keys MUST NOT appear in this field." / "the value of this field MUST be a URI pointing to a location where the key can be retrieved" — S063.txt:L249, L250 (§2.5.4)
> "it is always the security researcher's responsibility to make sure the key being specified is indeed one they trust" — S063.txt:L254 (§2.5.4)
The recommendation is narrowly scoped: encryption is RECOMMENDED when the contact value is an email address, and the field carries a retrieval URI — the RFC's three examples are an OpenPGP key over https, an OPENPGPKEY DNS record and an `openpgp4fpr:` fingerprint (§2.5.4). Signing is a separate, also-RECOMMENDED mechanism: "It is RECOMMENDED that a "security.txt" file be digitally signed using an OpenPGP cleartext signature" (§2.3), joined with the `Canonical` field so the signature authenticates the location (§2.3, §2.5.2) — and the two keys are not the same key ("Researchers must not assume that this key is used to generate the digital signature referenced in Section 2.3.", §2.5.4). Neither field conveys trust (§2.3, §5.1).

## Claim 3 — `Expires` is the staleness clock, and one year is the recommended horizon
> "indicates the date and time after which the data contained in the \"security.txt\" file is considered stale and should not be used" — S063.txt:L266 (§2.5.5)
> "It is RECOMMENDED that the value of this field be less than a year into the future to avoid staleness." — S063.txt:L270 (§2.5.5)
> "This field MUST always be present and MUST NOT appear more than once." — S063.txt:L273 (§2.5.5)
The value is an RFC 3339 timestamp (§2.5.5), and the RFC's own example value is already in the past. Read the direction literally: less than a year ahead is RECOMMENDED, so a date two years out is permitted by the format while telling a reader less than an annually refreshed file does. Past the stated instant the data is "stale and should not be used" (§2.5.5): the file does not expire silently, it expires by declaration.

## Claim 4 — `Policy` links the disclosure page, and the file itself lives under `/.well-known/`
> "The \"Policy\" field indicates a link to where the vulnerability disclosure policy is located." — S063.txt:L281 (§2.5.7)
> "organizations MUST place the \"security.txt\" file under the \"/.well-known/\" path" — S063.txt:L330 (§3)
> "For legacy compatibility, a \"security.txt\" file might be placed at the top-level path or redirect" — S063.txt:L333 (§3)
> "If a \"security.txt\" file is present in both locations, the one in the \"/.well-known/\" path MUST be used." — S063.txt:L335 (§3)
§3.1 repeats the division of labour: organizations SHOULD use this directive "to provide additional details regarding the scope and details of their vulnerability disclosure process", because the file carries a pointer while the page carries the prose — scope, authorization, timelines, rewards. The file's own location is §3's `/.well-known/security.txt` for a domain name or IP address, registered permanent in IANA's Well-Known URIs registry (§6.1). Retrieval is not free-form: the access "MUST use the \"https\" scheme" and the response "MUST have a Content-Type of \"text/plain\" with the default charset parameter set to \"utf-8\"" (§3), over HTTP 1.0 or higher (§3). When both locations resolve, the well-known copy is authoritative (§3), so a disagreeing top-level file is the legacy artifact.

## Claim 5 — scope is the retrieving host, not its neighbourhood
> "A \"security.txt\" file MUST only apply to the domain or IP address in the URI used to retrieve it, not to any of its subdomains" — S063.txt:L349 (§3.1)
> "Organizations SHOULD use the policy directive (as per Section 2.5.7) to provide additional details regarding the scope" — S063.txt:L357 (§3.1)
The restriction runs both ways — "not to any of its subdomains or parent domains" (§3.1) — while one file MAY also cover the products and services that the publishing organization provides (§3.1). Consequence: an `example.com` file does not speak for `shop.example.com`, and a subdomain's own file does not inherit the parent's contact.

## Claim 6 — redirects and staleness are the two ways a file stops being usable
> "researchers should record any redirects since they can lead to a different domain or IP address controlled by an attacker" — S063.txt:L528 (§5.2)
> "Not having a \"security.txt\" file may be preferable to having stale information in this file." — S063.txt:L536 (§5.3)
> "Organizations must use the \"Expires\" field (see Section 2.5.5) to indicate to researchers when the data in the file is no longer valid." — S063.txt:L538 (§5.3)
A redirect is allowed but must be recorded and inspected, because a compromised host can point the file at an attacker's copy (§5.1, §5.2); the protections the RFC names are the signature plus `Canonical` and a check of historical records (§5.1). Staleness is the other failure: outdated entries send reports to the wrong place, and the RFC prefers no file to a stale one (§5.3). A triager reads `Expires` before trusting `Contact`.

## Claim 7 — a file is a reporting channel, not a permission (F10: discovery channel vs policy text)
> "researchers shouldn't assume that the presence or absence of a \"security.txt\" file grants or denies permission for security testing" — S063.txt:L571 (§5.5)
This is the RFC drawing F10's line: `security.txt` answers where to report, to whom, in what language (§2.5.8), with what key (§2.5.4) and until when (§2.5.5); the disclosure policy page answers what a researcher may and may not do and how reports are handled (§2.5.7, §3.1). §5.5 says permission "may be indicated in the company's vulnerability disclosure policy (as per Section 2.5.7) or a new field" — never inferred from the file's presence, and never inferred from its absence either. Two rejected over-generalizations follow — that a published security.txt authorizes testing, and that its absence forbids testing — both falsified by §5.5, and §1.1's complementarity sentence forbids reading the file as a replacement for the policy page.

## Falsifiable rule and honest limit

**Falsifiable rule.** A statement about this standard is falsified by any of: (a) naming a REQUIRED field other than `Contact` and `Expires`, when §2.5 makes every field optional unless its own definition states otherwise, and only §2.5.3 and §2.5.5 do; (b) saying the file may carry a key, when §2.5.4 says "Keys MUST NOT appear in this field"; (c) treating `Expires` as advisory, when §2.5.5 makes it REQUIRED and single and §5.3 makes past-dated data unusable; (d) reading a top-level copy as authoritative beside a well-known one, when §3 says the well-known copy MUST be used; (e) extending a file to subdomains or parent domains, when §3.1 forbids it; (f) reading either presence or absence as a permission, when §5.5 says neither grants nor denies it.

**Honest limit.** One RFC, one capture: this covers the format and its stated rules, not whether any organization publishes a conforming file, and not the policy text a `Policy:` link points at. The document is Informational, so every MUST here binds the format, not a vendor.

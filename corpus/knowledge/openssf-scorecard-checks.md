## Claim 1 — maintenance is a 90-day commit-rate window, and young projects are unassessable by this check

The Maintained check's top score is time-boxed: "week during the previous 90 days, the project
receives the highest score." (S086.txt:415, Q6 — the sentence conditions the highest score on at
least one commit per week across the window), and the window is also a floor on assessability:
"This check will only succeed if a GitHub project is >90 days old." (S086.txt:428, Q7). Falsifiable
rule: a repository with no commit in the previous 90 days cannot hold this check's highest score,
and a repository younger than 90 days is unassessable by this check under the program's own rule —
both checkable against any Scorecard result for a known repository. Rejected over-generalization: a
low Maintained score is not an abandonment or vulnerability verdict — "of active maintenance is not
necessarily always a problem." (S086.txt:421, Q8); the doc itself scopes the signal to "potential
users should investigate further".

## Claim 2 — the Vulnerabilities check consumes the OSV service and performs no analysis of its own

Vulnerability detection is outsourced by the program's own text: the check "determines whether the
project has open, unfixed vulnerabilities in its own codebase or its dependencies using the [OSV
(Open Source Vulnerabilities)](https://osv.dev/) service." (S086.txt:710, Q10), and suppression is a
declared on-disk mechanism: "To ignore, create an `osv-scanner.toml` file next to the dependency
manifest" (S086.txt:718, Q11). Falsifiable rule: a Vulnerabilities finding traces to an OSV record,
and an ignored finding traces to an osv-scanner.toml declaration beside the dependency manifest — so
a suppressed finding is a project-authored decision, never a clean scan. Rejected
over-generalizations: this pins Scorecard's USE of OSV only — the OSV format's range/event semantics
stay F31/S080 and the KEV catalog stays F18/S052, neither of which this document defines; and "no
findings" is OSV-record-absence at scan time, not an absence of vulnerabilities.

## Claim 3 — risk tiers are per-check labels of what a LOW score indicates, conditionally worded

The doc labels each check's risk: Binary-Artifacts "Risk: `High` (non-reviewable code)"
(S086.txt:12, Q3), Dangerous-Workflow "Risk: `Critical`  (vulnerable to repository compromise)"
(S086.txt:286, Q4), Maintained "Risk: `High` (possibly unpatched vulnerabilities)" (S086.txt:411,
Q5), Webhooks "Risk: `Critical` (service possibly accessible to third parties)" (S086.txt:722, Q12),
Security-Policy "Risk: `Medium` (possible insecure reporting of vulnerabilities)" (S086.txt:592,
Q13). Falsifiable rule: every tier label is conditional — "possibly", "possible", "vulnerable to" —
so a tier grades the exposure a failing check INDICATES, and no tier asserts a confirmed condition
about any repository; testable by reading the label strings against their own wording. Rejected
over-generalization: a Critical-tier failing check is not evidence of compromise — the tier is the
program's impact prior, not a finding about a specific project, and nothing here asserts any
repository's actual state.

## Claim 4 — Security-Policy is a SECURITY.md presence-and-content detector, disjoint from F24's security.txt

The detection method is file presence: "works by looking for a file named `SECURITY.md`
(case-insensitive) in a few" well-known directories (S086.txt:595, Q14). Scoring is content-graded
in the doc's own rubric: 6/10 for link form (a valid email or http/https reporting address), 3/10
for free-form text beyond the link, 1/10 for specific vulnerability/disclosure text. Falsifiable
rule: a repository passes this check on SECURITY.md form alone — a policy naming none of F24's
security.txt fields still earns the link-form points, because the check reads a repo file, not the
/.well-known/security.txt discovery document. Rejected over-generalization: passing Security-Policy
asserts no working reporting channel; the partial-credit rubric is the doc's own evidence that form
is not function, and no claim is made about any policy's operational use.

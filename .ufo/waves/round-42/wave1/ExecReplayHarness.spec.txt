ExecReplayHarness.spec.txt — round-42 defeat catalog
=====================================================

Purpose
-------
This file is the map from every committed defeat artifact to (a) the repair
family it exercises, (b) the expected rejection mechanism the repaired limb
must exhibit, and (c) the catalog case id that materializes the defeat and
runs the limb.  ExecReplayHarness.sh is the executable form: it carries the
same catalog and exposes

    replay_defeat <artifact> <mode>
    replay_report   [mode]

where <mode> is fixture | export | list.  The L1 binds each family to its
own check through REPLAY_LIMB_MAP (or by accepting the default candidate
list in the library); the verdicts below are what the repaired round-42 suite
must produce.

Exit-code contract of replay_defeat
-----------------------------------
  0  every selected defeat was REJECTED by the current suite's limb, and the
     same limb ACCEPTED the pristine fixture (the control run).  The family is
     closed.
  1  at least one selected defeat was ACCEPTED by the limb: the family is
     still open.  This is the kill signal.
  2  not gradable: the limb is unresolvable, the fixture could not be
     materialized, or the limb rejected the PRISTINE fixture, so no verdict is
     attributable.  Never a silent pass.

The control run is what makes exit 0 meaningful.  A limb that rejects every
input would otherwise score every defeat as closed; requiring the pristine
fixture to be green makes that impossible.

Family -> limb binding
----------------------
The seven routed families and the limb that must reject their defeats:

  F-EVID   per-correction evidence          default limb check_j1 (fallback check_i1)
  F-TOKEN  token-boundary tallies           default limb check_j2 (fallback check_i3)
  F-TABLE  SKILL.md registry integrity      default limb check_j3 (fallback check_i7)
  F-DECL   declared-blocks completeness     default limb check_j4 (fallback check_i5, check_i12)
  F-SCAN   scratch hygiene                  default limb check_j5 (fallback check_i6)
  F-BIND   capture-binding variants         default limb check_j6 (fallback the capture-binding-check.py instrument)
  F-FLIP   frontier-counter status flip    default limb check_j7 (fallback the frontier-recheck-count.py instrument)

The J-ids are the round-42 suite's own checks (the claim's J1-J13); the
I-ids are the round-41 fallbacks, so one library drives both.  The J-ids were
read out of the frozen claim (`.ufo/waves/round-42/claims.json`, C1
predicate), which assigns J1 per-correction evidence (F-EVID), J2
token-boundary tally validation (F-TOKEN), J3 SKILL.md registry integrity
(F-TABLE), J4 declared-blocks completeness (F-DECL), J5 scratch-baseline
hygiene (F-SCAN), J6 capture-binding integrity (F-BIND) and J7
frontier-counter status-flip detection (F-FLIP); J8-J13 are receipt
integrity, negative controls, graded-selftest isolation, correction
uniqueness, no-deletion/density and scratch quiescence, which are outside the
seven routed families.  The L1 still pins the final mapping with
REPLAY_LIMB_MAP, e.g.

  REPLAY_LIMB_MAP='F-EVID=check_j1;F-TOKEN=check_j2;F-TABLE=check_j3;F-DECL=check_j4;F-SCAN=check_j5;F-BIND=check_j6;F-FLIP=check_j7'

F-EVID payload vocabulary (measured)
------------------------------------
`evidence=<n>/<m>` counts MEMBERS — correction blocks — not identifiers:
`m` is the member total (4 on the round-41 record set: SCORECARD.md L1602 and
L1607, LOG.md L1736, SHONEN.md L221) and `n` is how many of them name all
three identifiers.  The identifier set itself is fixed at the three round-41
stems (RevC1Counters, CritKillRule, MutH6H10) and must not be widened.
`union=<k>/3` is the cross-record overlap of those identifiers and stays 3/3
on every mutant below — that is the defect the per-block rule closes.
`graded=<n>/<m>` has the same member shape for the verdict clause.

Measured readings on the landed J1 (lane HEAD 514ff62, fixture = lane export
plus the round-40/wave2 grounding tree):

    pristine   evidence=4/4 closed=1 rc=0  union 3/3
    e4         evidence=1/4 closed=0 rc=1  union 3/3  fail=SCORECARD.md:1602;LOG.md:1736;SHONEN.md:221
    e1         evidence=2/4 closed=0 rc=1  union 3/3  fail=1602;1607
    e2         evidence=3/4 closed=0 rc=1  union 3/3  fail=LOG.md:1736
    e3         evidence=3/4 closed=0 rc=1  union 3/3  fail=SHONEN.md:221

These totals are taken with J1's default `J1_ROUNDS=(41)`.  If the L1 later
enables the round-42 block (`J1_ROUNDS=(41 42)` plus `J1_EVIDENCE_MAP[42]`),
the payload keeps its GRAMMAR and only the totals move: `rounds=1` becomes
`rounds=2`, `lines=` becomes the sum over both blocks, `detail=` gains an
`r42:` group per record, and `evidence=<n>/<m>` keeps its member-count
meaning now taken over both blocks.  `closed=0|1` and `fail=` keep their
meaning, and the three round-41 stems stay fixed (round 42 declares its own).
Read `rounds=` to know which block set produced the totals.  The rejection
key is invariant: `closed=0` or a nonzero exit, which is what the library
tests; a `rounds=2` reading is the documented extension, not drift.

Fixture requirement for F-EVID / F-TOKEN
----------------------------------------
A round-42 J1 limb GROUNDS each declared evidence identifier in the committed
wave-2 artifact that carries it and fails `evidence-not-grounded` when those
files are absent.  The grounding round is NOT the running suite's round: the
r42 J1 audits the round-41 correction blocks (`J1_ROUNDS=(41)`) and therefore
grounds under `.ufo/waves/round-40/wave2` even when the r42 suite runs.

The library therefore carries EVERY `.ufo/waves/round-4*/wave2` tree the
export holds in every F-EVID / F-TOKEN fixture — a superset, because a
round-token-derived path would carry the wrong tree for a limb that audits an
earlier round, and the pristine control would then red with
`evidence-not-grounded`, making the case UNGRADED (exit 2) rather than
gradable.  A records-only fixture is refused the same way: control red,
UNGRADED, never a silent pass.

J1 polarity (confirmed by that seat): `check_j1` exits 0 with `closed=1` when
the defect is absent and exits 1 with `closed=0` when it is present.  The
library's rejection test is `rc != 0` OR output contains `closed=0`, so J1's
red maps to REJECTED as required.  `check_j1` reads `$1` only.

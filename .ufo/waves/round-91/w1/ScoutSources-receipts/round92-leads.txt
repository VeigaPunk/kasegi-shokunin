  Why the account SAS still closes the Azure question — the two Azure limits are measured
  against the DOCUMENTED field set, and the documented set does not reach either limit:
    (a) PARAMETER-NAME LENGTH window. Measured boundary on the landed scanner: a 7-letter
        name between the version and signature parameters still detects; an 8-letter name
        does not. The longest parameter name documented anywhere in the Azure user-delegation
        and account-SAS pages is 7 letters (the delegated-tenant field). Every documented
        Azure SAS field name is 2-7 lowercase letters, so the round-91 widening to 2-7
        covers 100% of the documented names. Measured name-length sweep: 7 letters -> hit,
        8 letters -> miss.
    (b) PARAMETER-COUNT window. Measured boundary on the landed scanner: 20 intervening
        parameters still detect, 21 do not. Clean sweep, each n being its own list of n
        distinct 3-letter names between the version and signature parameters:
        n=15 -> hit, n=16 -> hit, n=17 -> hit, n=18 -> hit, n=19 -> hit, n=20 -> hit,
        n=21 -> miss, n=22 -> miss.
        The union of ALL 21 documented Azure SAS field names (excluding the version and the
        signature parameters) is 21, but that union is not a real token: several of those
        fields are mutually exclusive alternatives. The widest realistic token measured — a
        user-delegation SAS carrying 16 documented fields — detects.
    So both Azure limits are unreachable with any token Microsoft documents. This is the
    round-92 answer for the Azure axis: nothing to extend, and a name-length or count
    widening would be un-motivated by the sources.

  RULED OUT, so it is not re-chased next round: the hypothesis that a 9-letter Azure SAS

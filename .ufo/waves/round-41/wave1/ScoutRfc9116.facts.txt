2. Well-known URI (Section 3 "Location of the security.txt File", capture lines 437-446)
- Requirement sentence (lines 439-441, 13 words): "For web-based services, organizations MUST place the "security.txt" file under the "/.well-known/" path"
- Full rule context: per [RFC8615] of a domain name or IP address; legacy top-level placement allowed only as redirect; if both locations present, the "/.well-known/" copy MUST be used (lines 442-446).
- Access rule: "The file MUST be accessed via HTTP 1.0 or a higher version, and the file access MUST use the "https" scheme ... It MUST have a Content-Type of "text/plain" with the default charset parameter set to "utf-8"" (lines 448-451).
- Scope: "A "security.txt" file MUST only apply to the domain or IP address in the URI used to retrieve it, not to any of its subdomains or parent domains" (Section 3.1, lines 460-462).

- Per-field table (name — section — requirement level — evidence lines):

  - Canonical — 2.5.2 (line 264) — optional by default; web URI MUST begin "https://" (lines 268-270); if the retrieval URI is not listed in any Canonical field the file contents SHOULD NOT be trusted (lines 276-278)

4. Expires field semantics incl. the one-year rule (Section 2.5.5, capture lines 341-353)
- Semantics (lines 343-345): "The "Expires" field indicates the date and time after which the data contained in the "security.txt" file is considered stale and should not be used (as per Section 5.3)."
- Format (lines 345-347): value formatted per the Internet profiles of ISO.8601-1/-2 as defined in RFC3339.
- One-year rule (lines 347-349): "It is RECOMMENDED that the value of this field be less than a year into the future to avoid staleness."
- Presence rule (line 351): "This field MUST always be present and MUST NOT appear more than once."
- Worked example (line 353): "Expires: 2021-12-31T18:37:07z"

5. Encryption field text (Section 2.5.4, capture lines 314-322)
- Definition (lines 316-319): "The "Encryption" field indicates an encryption key that security researchers should use for encrypted communication. Keys MUST NOT appear in this field. Instead, the value of this field MUST be a URI pointing to a location where the key can be retrieved."
- Web-URI rule (lines 319-321): "If this field indicates a web URI, then it MUST begin with "https://" (as per Section 2.7.2 of [RFC7230])."
- Verification duty (lines 323-325): authenticity verification is always the researcher's responsibility; the key must not be assumed to be the Section 2.3 signature key.
- Examples (lines 327-335): https URI, OPENPGPKEY DNS record, openpgp4fpr fingerprint.

6. Security Considerations pointer (Section 5, capture line 680)
- The file itself as attack surface when unsigned/stale/compromised:
  - Section 5.1 "Compromised Files and Incident Response" (line 686), lines 688-689: "An attacker that has compromised a website is able to compromise the "security.txt" file as well or set up a redirect to their own site." Mitigations named at lines 697-700: use the Canonical field, digitally sign the file (Section 2.3), monitor for tampering; researchers should verify the digital signature and check historical records before use (lines 702-704).
  - Section 5.3 "Incorrect or Stale Information" (line 721), lines 723-728: stale or incorrect data misroutes reports "thus exposing possible security issues to third parties. Not having a "security.txt" file may be preferable to having stale information in this file."
  - Section 5.4 "Intentionally Malformed Files, Resources, and Reports" (line 737), lines 743-745: parsers may refuse "files larger than 32 KBs, those with fields longer than 2,048 characters, or those containing more than 1,000 lines"; the Section 4 ABNF grammar is the validity check.
  - Section 5.2 "Redirects" (line 713) and 5.7 "Protecting Data in Transit" (line 782) cover redirect and transport trust.

7. IANA registration section (Section 6, capture line 836)
- 6.1 "Well-Known URIs Registry" (line 842): IANA updated the Well-Known URIs registry — URI suffix "security.txt", change controller IETF, specification RFC 9116, status "permanent" (lines 844-850). Resources referenced inside a security.txt MUST NOT point into the Well-Known URIs namespace unless registered with IANA (lines 837-840).
- 6.2 "Registry for security.txt Fields" (line 852): created per RFC8126; new registrations/updates under Expert Review (lines 857-859); each new field thus registered "is considered optional by this specification" (lines 859-861). Initial registry (lines 878-950) lists the eight fields of item 3 with Multiple Appearances flags: Acknowledgments yes, Canonical yes, Contact yes, Expires no, Encryption yes, Hiring yes, Policy yes, Preferred-Languages no.

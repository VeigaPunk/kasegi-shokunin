## Scope and decision rule

This entry records the maintainer side of one GitHub feature: what the platform documents for a repository maintainer who already knows about a vulnerability in a public repository and must carry it through to publication. The source is a single GitHub Docs overview page, captured whole (42 lines, S074.txt:1-42; the whole capture is body prose, with no navigation chrome). The page scopes the feature itself: “Repository security advisories and private vulnerability reporting are available for public repositories on GitHub.com” (S074.txt:6). Its one-line summary is the whole lifecycle: “You can use repository security advisories to privately discuss, fix, and publish information about security vulnerabilities in your public repository.” (S074.txt:3).

Decision rule. A package may describe a maintainer's advisory step as GitHub-conformant only when the package records, from this page: that the advisory was drafted and the discussion held privately before anything was published; that the fix was developed privately; that the CVE identification number was requested from GitHub while the advisory was still private; that a fix version is attached before publication or its absence is stated; and that credit is recorded. Publication is the step that changes what the world can see, so the package orders its claims: private steps first, publish last. The private phase is the page's “Repository security advisories allow maintainers of public repositories to privately discuss and fix a security vulnerability in a project.” (S074.txt:10); the public phase is “Publish the security advisory to alert your community of the vulnerability once a patch is released.” (S074.txt:14), which ties publication to a released patch.

Two further page facts bound the package's claims. The CVE path is a request to GitHub, not an automatic assignment: when the project holds no identifier yet, “you can request a CVE identification number from GitHub.” (S074.txt:25), and “If your security advisory is eligible for a CVE, GitHub will reserve a CVE identification number for your advisory.” (S074.txt:25). The identifier leaves GitHub only after publication: “GitHub publishes the CVE to the MITRE database.” (S074.txt:27). Visibility after publication is graded, not uniform: “Anyone can see the current version of the advisory data, as well as any advisory credits that the credited users have accepted.” (S074.txt:31) and “Collaborators can view the conversation history of the advisory.” (S074.txt:32), while “The URL of a security advisory does not change after publication.” (S074.txt:33).

## Limits

- The page also names a security-policy flow (S074.txt:18), an npm mirror (S074.txt:20) and the GitHub Security Lab (S074.txt:21) without holding their bodies. The dependency-graph publishing rule is stated only in the overview sentence at S074.txt:19.
- The fix-version guidance is conditional prose, not a schedule: “Imminently available, and you are able to, wait to disclose the issue when the fix is ready.” (S074.txt:40), “In development but not yet available, mention this in the advisory, and edit the advisory later, after publication.” (S074.txt:41) and “Not planned, be clear about it in the advisory so that your users don't contact you to ask when a fix will be made.” (S074.txt:42). ## Falsifiable package rule

A package advisory step is GitHub-conformant only if all of the following hold, each located on this page: (1) the advisory is drafted privately before publication and the discussion stays in the draft (S074.txt:10, S074.txt:12); (2) the fix is developed in the temporary private fork (S074.txt:13); (3) the CVE identification number is requested from GitHub while the advisory is still private, with the 72-hour review recorded as the page's stated expectation and never as a guarantee (S074.txt:25); (4) the package never claims that the CVE request itself publishes the advisory (S074.txt:25); (5) before claiming a GitHub-assigned identifier, the package checks the other-CNA boundary (S074.txt:26); (6) a fix version is added before publication, or the package states that none exists (S074.txt:38); (7) credit for contributors is recorded (S074.txt:17); and (8) publication visibility is stated as the page states it, not as full disclosure of the conversation (S074.txt:31, S074.txt:32). A package that fails any clause is not GitHub-conformant on this page's evidence, and the failure is recorded as unknown rather than as a yes.

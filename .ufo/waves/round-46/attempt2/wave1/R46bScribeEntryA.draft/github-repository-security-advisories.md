## Scope and decision rule

This entry records one maintainer-side flow: the route GitHub documents for a project maintainer who must discuss, fix and publish a security vulnerability in a public repository. The source is one GitHub Docs page; its body prose is S074.txt:8-42 and the rest of the capture is page chrome and site navigation. It is not a rule for other platforms, for private repositories, or for coordinated disclosure in general.

The object is defined on the page as: “Repository security advisories allow maintainers of public repositories to privately discuss and fix a security vulnerability in a project.” (`S074.txt:10`) The page then lists the three actions the feature supports: “Create a draft security advisory, and use the draft to privately discuss the impact of the vulnerability on your project.” (`S074.txt:12`) “Privately collaborate to fix the vulnerability in a temporary private fork.” (`S074.txt:13`) “Publish the security advisory to alert your community of the vulnerability once a patch is released.” (`S074.txt:14`)

The identifier path runs through GitHub itself: “GitHub is a CVE Numbering Authority (CNA) and is authorized to assign CVE identification numbers.” (`S074.txt:24`) The request carries a clock and a non-effect: “GitHub usually reviews the request within 72 hours.” (`S074.txt:25`) “Requesting a CVE identification number doesn't make your security advisory public.” (`S074.txt:25`) The page also draws the boundary against other numbering authorities: “GitHub cannot assign CVEs to your project if it is covered by another CNA.” (`S074.txt:26`) The requester is not anonymous: “Anyone with admin permissions to a security advisory can request a CVE identification number.” (`S074.txt:25`)

Publication is where the private record becomes a public one, and the page states who sees what: “Anyone can see the current version of the advisory data, as well as any advisory credits that the credited users have accepted.” (`S074.txt:31`) The conversation itself stays with collaborators: “Collaborators can view the conversation history of the advisory.” (`S074.txt:32`) Credit is offered as a first-class field: “You can give credit to individuals who contributed to a security advisory.” (`S074.txt:17`) The remaining precondition is the fix version: “you should add a fix version to a security advisory prior to publishing the advisory” (`S074.txt:38`)

Decision rule for a package: a step may be described as a GitHub repository security advisory step only when the package records all three of these facts from the page: (1) the advisory was drafted while the vulnerability was still private, (2) the CVE identification number was requested from GitHub while the advisory was still private, and (3) a fix version was attached before publication. A package that describes a CVE request as the publication event, or that publishes an advisory with no fix version while describing a safe upgrade for its users, contradicts the page and fails this entry's rule. Where the package's project is covered by another CNA, the request step must not be described as a GitHub assignment. Where the fix is not yet available, the page's own alternatives apply: wait to disclose, or disclose and say the fix is in development, or disclose and say no fix is planned (`S074.txt:39-42`).

Neither entry absorbs the other: F28's page does not state the maintainer-side flow, and this page does not state the reporter's form fields or the enablement condition.
- corpus/knowledge/cna-assignment-and-vulnerability-rules.md:9-13 (F07) holds the program's own assignment rules. That entry holds that a local CVE-request package review separates technical vulnerability determination, CNA assignment scope, and identifier counting (corpus/knowledge/cna-assignment-and-vulnerability-rules.md:9), and it holds the program's routing rule that the CNA with the most appropriate scope gets the first opportunity to assign (corpus/knowledge/cna-assignment-and-vulnerability-rules.md:36). What is new here: the maintainer-side draft-to-publication cycle with its two clocks (the 72-hour CVE review at `S074.txt:25` and the separate Dependabot publication clock at `S074.txt:36`), the private-fork collaboration step (`S074.txt:13`), the credit field (`S074.txt:17`), the publication visibility split between the public advisory data and the collaborators-only conversation (`S074.txt:31-32`), and the fix-version duty (`S074.txt:38`). ## Falsifiable package rule

A package advisory step is GitHub-conformant only if all of the following hold, each traceable to this page: (1) the advisory exists as a draft before publication, so that the discussion of the impact stayed private (`S074.txt:12`); (2) the fix was developed in the temporary private fork and the advisory is published only once a patch is released (`S074.txt:13`, `S074.txt:14`); (3) the CVE identification number was requested from GitHub while the advisory was still private, and the package does not describe that request as the publication event (`S074.txt:24`, `S074.txt:25`); (4) the package does not claim a GitHub assignment for a project covered by another CNA (`S074.txt:26`); (5) a fix version is recorded on the advisory before publication, or the package states that no fix version exists instead of implying a safe upgrade (`S074.txt:38`); (6) the package's visibility statements match the page: advisory data and accepted credits are public, the conversation history is collaborator-only, and the advisory URL is stable after publication (`S074.txt:31`, `S074.txt:32`, `S074.txt:33`); and (7) the package records the CVE review clock as a usual 72 hours and does not promise a deadline the page does not state (`S074.txt:25`). A package that fails any of these is not GitHub-conformant on this evidence, and the reviewer must not read the platform's silence on the missing condition as permission.

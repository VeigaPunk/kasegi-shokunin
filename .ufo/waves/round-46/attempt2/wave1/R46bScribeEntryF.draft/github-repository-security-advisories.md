## Scope and decision rule

This entry records the maintainer side of one GitHub Docs overview page: what a public repository's maintainer may do with a repository security advisory before and at publication. The capture is 42 lines and the whole capture is body (S074.txt:1-42); it is GitHub's own statement, not a general disclosure standard, not a rule for other platforms, and not a record of any repository's actual advisory.

The private phase. “Repository security advisories allow maintainers of public repositories to privately discuss and fix a security vulnerability in a project.” (`S074.txt:10`) The advisory starts as a draft: “Create a draft security advisory, and use the draft to privately discuss the impact of the vulnerability on your project.” (`S074.txt:12`) The fix is developed in a private space: “Privately collaborate to fix the vulnerability in a temporary private fork.” (`S074.txt:13`) The advisory may credit contributors: “You can give credit to individuals who contributed to a security advisory.” (`S074.txt:17`)

The identifier phase. The platform is the numbering authority: “GitHub is a CVE Numbering Authority (CNA) and is authorized to assign CVE identification numbers.” (`S074.txt:24`) A request is reviewed on a clock: “GitHub usually reviews the request within 72 hours.” (`S074.txt:25`) The request is not publication: “Requesting a CVE identification number doesn't make your security advisory public.” (`S074.txt:25`) When another numbering authority already covers the project, the platform stands down: “GitHub cannot assign CVEs to your project if it is covered by another CNA.” (`S074.txt:26`)

The publication phase. Publication alerts the community: “Publish the security advisory to alert your community of the vulnerability once a patch is released.” (`S074.txt:14`) A published advisory is publicly readable: “Anyone can see the current version of the advisory data, as well as any advisory credits that the credited users have accepted.” (`S074.txt:31`) A fix version is expected before publication: “you should add a fix version to a security advisory prior to publishing the advisory” (`S074.txt:38`)

Two 72-hour clocks must not be merged: the CVE-request review clock above (S074.txt:25) and the Dependabot-alert clock, “This process can take up to 72 hours and GitHub may contact you for more information.” (`S074.txt:36`)

Decision rule (the rule a package can act on). A package may describe a maintainer's advisory step as GitHub-conformant only when all three of these are recorded from this page: (1) draft before publish — the advisory existed as a draft before it was published (S074.txt:12); (2) fix version before publish — a fix version was attached before publication, or the package records that none was set and states the consequence (S074.txt:38); (3) CVE request while private — any CVE identification number was requested from GitHub while the advisory was still private, and no CVE is credited to the project unless the platform reserved one for that advisory (S074.txt:24, S074.txt:25). A package that claims a published advisory with no fix version, or that treats a CVE request as publication, fails the rule.

## Overlap and novelty

Contrast with the reporter-side twin held as F28, corpus/knowledge/github-private-vulnerability-reporting.md:9-13 and corpus/knowledge/github-private-vulnerability-reporting.md:15-24. That entry's actor is the person who found the vulnerability and its lifecycle stage is intake: the enablement precondition, the report form's default fields, the submission effects and the maintainer-only merge from the private fork, all read from S073. This entry's actor is the repository maintainer and its lifecycle stage is handling after intake: the private draft, the private fork where the fix is developed, the credit, the platform's CNA seat and its request clock, the other-CNA boundary, the published visibility and the fix-version duty, all read from S074. The contrast is of coverage: F28 covers the reporter's half of one flow and this entry covers the maintainer's half, the two pages do not contradict each other, and neither entry absorbs the other's rows. A package must not read the reporter-side enablement condition as a maintainer-side rule, nor read the maintainer-side publication duty as a reporter-side right.

Contrast with F07, corpus/knowledge/cna-assignment-and-vulnerability-rules.md:9-13 and corpus/knowledge/cna-assignment-and-vulnerability-rules.md:30-38. F07 holds the CVE Program's assignment scope for numbering authorities as organisations: each CNA operates within a scope definition, an appropriate CNA is given the first opportunity to assign, and separate identifiers follow independently fixable vulnerabilities; its source is the CNA operational rules PDF (S031). This entry holds the platform's per-advisory request instead: the platform's own CNA seat (S074.txt:24), the review clock on one request (S074.txt:25), the reservation that follows a made-public advisory (S074.txt:25), and the boundary where the platform declines to assign (S074.txt:26). The two are different scopes: F07 governs what a numbering authority organisation may assign at all, this entry governs one platform's handling of one advisory, so a package satisfying this entry's request steps does not satisfy F07's scope rules, and the other way round.

What is new here: the maintainer-side lifecycle ground — the private draft, the temporary private fork as the fix workspace, the credit step, the platform as CNA with its 72-hour request review, the no-publication effect of a CVE request, the other-CNA boundary, the published visibility levels, and the fix-version duty with its stated consequence for dependency alerts. ## Falsifiable package rule

A package advisory step is GitHub-conformant only if every one of these is recorded from S074, in this order. (1) Draft before publish: the package shows the advisory existed as a draft before publication — “Create a draft security advisory, and use the draft to privately discuss the impact of the vulnerability on your project.” (`S074.txt:12`). (2) Private fix: the package shows the fix was developed in the private collaboration space — “Privately collaborate to fix the vulnerability in a temporary private fork.” (`S074.txt:13`). (3) CVE request while private: the package shows the identifier was requested from GitHub before publication, and it does not present the request as publication — “Requesting a CVE identification number doesn't make your security advisory public.” (`S074.txt:25`) — nor does it claim a CVE the platform did not reserve for that advisory (“GitHub is a CVE Numbering Authority (CNA) and is authorized to assign CVE identification numbers.” (`S074.txt:24`)). (4) Fix version before publish: the package shows a fix version attached before publication, or it records that none was set and states the consequence — “you should add a fix version to a security advisory prior to publishing the advisory” (`S074.txt:38`). A package that shows a published advisory with no fix version, or that treats a CVE request as publication, or that claims a CVE for a project covered by another CNA (S074.txt:26), fails this rule.

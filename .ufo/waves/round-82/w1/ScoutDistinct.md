## D1 — the entry's Appendix A attribution is wrong: F31 holds 2 of Appendix A's 4 validation rules, not the appendix

**Severity:** medium (a distinctness/disposition misstatement; it makes an unopened first-party
surface look mined, so a later round would skip it).

**Where:** `corpus/knowledge/osv-high-quality-record-import-bar.md:70` (the `Not claimed` paragraph),
repeated at `corpus/README.md:1257` (the F58 frontier row's `next` cell).

> "Appendix A (S116.txt:63-86), which the page itself labels as generated by Gemini from the OSV
> JSON schema (S116.txt:64) — a summary of the schema, **held at its source by F31 / S080**."

README :1257 makes the same attribution: "the Gemini-generated Appendix A (:63-86) stay unclaimed
**(held by F31)**".

**Falsifiable ground.** Appendix A's four "Additional Validation Rules" are at `S116.txt:83-86`.
Measured against F31's own ground `corpus/source-snapshots/round-50/S080.txt` and F31's entry
`corpus/knowledge/osv-affected-range-events.md`:

| Appendix A rule | S116 line | counterpart in S080 | cited by F31? | held by F31? |
|---|---|---|---|---|
| `timestamp` = custom RFC3339 definition | :83 | RFC3339 at S080:371, :383, :389 | **no** — `grep -c RFC3339` on the F31 entry = 0 | **no** |
| `additionalProperties: false` | :84 | **0 hits in S080**; `grep -rc additionalProperties` S080=0, S116=1 | n/a | **no** |
| conditional validations, e.g. `repo` required when type is GIT | :85 | S080:788 | yes — F31 entry:78 (`Q12`) | **yes** |
| `last_affected` specified ⇒ `fixed` absent | :86 | S080:760-761 | yes — F31 entry:60 | **yes** |

So **2 of 4** are held by F31, not all. `additionalProperties: false` — the rule that makes the
schema closed to extra properties — has no counterpart in S080 at all.

**The stronger, dispositive point:** the thing Appendix A is a summary of — **the OSV JSON Schema
artifact** — has never been opened in this lane. `grep -rl "ossf/osv-schema" corpus/source-snapshots/`
= 0 files; the schema is only *pointed at* by `S080.txt:27-28` ("A JSON Schema for validation is
also available here."). And S080's own registry row
(`corpus/SOURCES.md:86`) explicitly scopes S080 with "**not the JSON Schema validation artifact**".
So "held at its source by F31 / S080" is false in the strict sense: F31/S080 is not the source of
Appendix A, and it is the lane's own row that says so. The registry even already models the
correct pattern — an unopened companion becomes a **lead** (as "Managing the Perishability of OSV
Records" correctly did at `corpus/SOURCES.md:182`), and no such lead exists for the OSV JSON Schema.

**Why this matters for the judged axes.** depth:verifiability — the sentence tells a re-verifier
that the ground is covered, so the JSON Schema is never opened. coverage — a first-party OSV
surface named by the newly admitted source itself (`S116.txt:64` "from the OSV JSON schema") goes
unrecorded as a lead.

**Routed defect.** Correct entry :70 and README :1257 to attribute only the two rules F31 actually
holds (`:85` → S080:788 / F31:78; `:86` → S080:760-761 / F31:60), and record the OSV JSON Schema as
an unopened lead in `corpus/SOURCES.md`'s Leads section. Note the sibling's `lesson-round-82.md:164`
carries the same "held at its source" wording and needs the same correction.
